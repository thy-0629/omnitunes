# 搜索韧性与结果体验设计

## 目标

让搜索结果反映每个音源实际返回的内容，而不是因为一次播放预检失败而消失；保留用户点击播放的机会，并在原卡片中给出可理解的失败原因。同时修复搜索框双清空、歌手检索和搜索结果滚动/底栏遮挡。

## 已确认的产品决策

- 搜索命中与“当前可播放”分离。已从音源检索到的项目必须显示，即使播放预检暂时超时或失败。
- 搜索卡片上的每个来源都携带可播放状态：可播放时正常显示；暂不可播放时显示“当前无法播放”。
- 暂不可播放的来源仍可被点击。点击后重新解析/验证播放；若仍失败，在同一来源行显示具体原因和可重试提示，不用全局错误替代结果。
- 纯歌手查询应匹配歌曲标题、已解析的歌手和来源作者/上传者。来源作者只用于检索线索和展示发布者，不能在缺乏可靠信息时冒充歌曲歌手。
- 互联网档案馆、Openverse 与 Wikimedia Commons 的曲库范围不覆盖大多数中文商业音乐；没有命中时如实显示，而不合成或伪造结果。
- 搜索框只保留一个清空入口；采用自定义按钮并隐藏 Chromium `type=search` 的原生取消控件。
- 搜索结果在固定视口的主内容区滚动，底部播放条高度被动态预留，最后一项永远可滚动到完整可见。

## 方案比较

### 方案 A：保留所有命中并附带播放状态（采用）

检索阶段先规范化所有有效命中；播放预检产出每个来源项的状态与失败详情，而不是决定该项是否存在。优点是多源结果可见、故障原因精确且用户可重试；代价是需要扩展搜索 API 数据合同和前端行状态。

### 方案 B：继续仅显示已预检可播结果

保持当前后端结构，只优化报错文案。实现小，但会继续造成“只有 B 站”的误导，不满足确认的交互。

### 方案 C：完全取消播放预检

搜索最快且结果最多，但播放失败会集中到点击后，失去搜索结果中的即时可用性提示。因此不采用。

## 架构与数据流

1. 每个音源适配器返回 `RawHit` 后，搜索服务先将该命中规范化为可展示的歌曲、录音和来源项。
2. 播放预检独立运行，并把结果保存为来源项的瞬态搜索状态：`playable`、`unavailable` 或 `unknown`；不可播放状态包含机器码、用户可读原因和可选重试时间。
3. 搜索 API 将状态随来源项返回。前端在来源行内显示状态徽标和一条紧凑的失败原因；相同音源的重复预检错误汇总，不再重复渲染全局警告。
4. 用户点来源行时，播放器沿用现有解析/回退路径并再次验证。如果失败，播放器把该来源项 ID 与原因回传给搜索状态，来源行更新为失败说明，同时不会影响其他结果。
5. 检索匹配分为标题、歌手与发布者三类。标题和可靠歌手匹配用于排序；发布者只作为较弱的召回信号。纯歌手查询不再被当作“必须出现在标题中”。

## UI 与布局

- 将 `type=search` 的浏览器取消按钮设为不可见，仅渲染既有、可访问的“清空”按钮。
- 来源行使用状态文本而非只用颜色：例如“当前无法播放 · Archive 元数据请求超时”。该行仍保留播放操作；点击后的新失败覆盖为最新原因并提供重试操作。
- `AppShell` 固定为视口高度的纵向弹性布局，`main` 成为唯一的可滚动内容区。通过 CSS 变量或稳定的播放器高度预留空间，避免固定播放器遮挡末项。
- 20 条搜索上限不变；本次不加入无限加载，避免把“能滚动查看已有结果”与“加载更多”混为一项行为。

## 错误处理与边界

- 音源搜索请求本身失败：保留其他音源结果，并在搜索结果顶部每个音源仅显示一条汇总错误。
- 单条播放预检失败：仅影响相应来源行，不影响同组歌曲或其他来源。
- 没有来源命中：显示当前的空态，并明确查询的音源范围。
- 用户点击不可播放来源：重新验证；失败时显示当次原因，成功则正常开始播放并更新为可播放。

## 测试与验收

1. 非 B 站命中在预检超时时仍出现在搜索结果，并标有不可播放状态；可播放来源仍可照常播放。
2. 点击不可播放来源会执行重新解析；失败原因显示在同一行而不清空搜索结果。
3. 相同音源多条预检失败只出现一条汇总全局错误。
4. 纯歌手查询能召回歌曲名不含该歌手、但可靠歌手或发布者字段匹配的结果；歌曲标题精确匹配仍优先于弱发布者匹配。
5. 搜索框只有一个可见的清空按钮。
6. 在桌面和窄屏视口，搜索结果能滚动到底，最后一张卡片不被播放器遮挡。
7. 后端与前端单元测试、类型检查和生产构建通过。
