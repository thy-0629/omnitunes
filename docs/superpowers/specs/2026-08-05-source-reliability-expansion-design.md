# Omnitunes 稳定音源扩展设计

## 目标

在不要求用户提供 API Key、也不抓取受限制平台内容的前提下，扩展可播放音源，并将“实际能播放”置于结果数量之前。主流中文歌曲仍以 Bilibili 官方嵌入为主；开放授权、独立和公共领域音乐由多个可验证的直链音源补充。

## 范围与平台边界

- 保留现有 Bilibili 官方嵌入、当地文件和 Internet Archive。
- 新增 Openverse 开放授权音频和 Wikimedia Commons 开放媒体音频。
- 不接入抖音搜索抓取、盗链、深度链接、模拟下载或音频提取；抖音官方协议禁止这些方式，且其开放能力不提供全站公共音乐检索/播放。
- 不接入 YouTube，因为用户不配置 API Key 且网络可用性不确定。
- Jamendo 只保留为未来的可选用户配置来源；本次不使用其测试 client ID，也不要求用户注册。
- 不下载或缓存第三方媒体文件；仅取得公开、允许播放的原始媒体 URL 并由浏览器播放。

## 来源分层

| 层级 | 来源 | 默认状态 | 播放方式 | 内容定位 |
| --- | --- | --- | --- | --- |
| 主流视频音乐 | Bilibili | 启用 | 官方 iframe | 主流中文歌与视频音乐 |
| 本地 | Local | 启用 | 本地/原生音频 | 用户自己的文件 |
| 开放音频 | Internet Archive | 启用，但严格验证 | 原生 stream | 公共领域、现场、历史录音 |
| 开放音频 | Openverse | 启用，但严格验证 | 原生 stream | 聚合的 CC/公共领域音乐与音频 |
| 开放媒体 | Wikimedia Commons | 启用，但严格验证 | 原生 stream | 古典、现场、教育和公共领域音频 |
| 未来可选 | Jamendo | 禁用 | 原生 stream | 独立音乐；仅在用户自行配置 client ID 后启用 |

新来源 ID 固定为 `openverse` 和 `wikimedia`。现有 Archive ID `open_source` 保持不变，避免已有数据库、收藏和队列失效。

## 可播放性优先的数据流

搜索不再把“搜索接口返回了元数据”等同于“可播放”。每一个候选来源须经过下列分层验证：

1. **适配器筛选。** Archive 只保留能在元数据中找到受支持音频文件的条目；Openverse/Commons 只保留带有效原始音频 URL、非敏感且授权信息完整的音频条目。Bilibili 保留符合官方 embed 标识格式的条目。
2. **预检。** 对原生 `stream` 候选，后端以受限的 `Range: bytes=0-1` 请求确认响应是可访问的媒体（HTTP 200/206、非 HTML 错误页、大小受限的响应）。每个来源只预检排序最前的有限候选，并设置总并发数、超时和短期内存缓存，避免搜索被慢源拖垮。
3. **结果门槛。** 未通过预检的 `stream` 来源不进入统一搜索结果；预检超时/网络异常记为该来源的局部错误，不影响其他来源结果。官方 iframe 来源不伪造结束/可播放状态，只显示为可嵌入来源。
4. **播放期反馈。** 原生 `<audio>` 报错时，既有换源逻辑继续尝试同一歌曲的其他来源；失败的 source item/option 被短期标为不可用，之后的搜索和自动挑选会降权或跳过它，直到冷却期重新预检。

预检仅验证可访问性，不代理、存储、转码或下载媒体。播放器最终仍直接使用适配器返回的 URL。

## 适配器与契约

在现有 `SourceAdapter` 之上增加可选的“搜索可播放性验证”能力，而不是让页面自行探测链接。适配器返回的候选必须能表达：来源 ID、授权/归属信息、预期的播放类型，以及是否需要 stream 预检。

统一搜索服务在规范化前调用验证层；只有通过验证的 `RawHit` 被写入 `SongWork → Recording → SourceItem`。播放编排器继续在真实播放时重新解析选项，并复用短期验证缓存，不相信过期的搜索期结论。

- **Archive:** 对有限的候选并发读取 item metadata，从支持的 `mp3/m4a/ogg/flac` 文件中挑选可公开访问的一个或两个选项；预检成功才展示。
- **Openverse:** 使用匿名音频搜索，限定 `category=music`，排除敏感条目；保存原始 URL、创作者、来源页、许可证与署名文本。只有预检成功的直链才展示。界面保留“授权/署名”可见入口，不把开放授权误写成平台官方发布。
- **Wikimedia Commons:** 使用官方 MediaWiki 查询搜索音频文件，读取文件页元数据和原始文件 URL；保存创作者、许可证和 Commons 文件页，预检成功才展示。

每个来源实现独立的 `search()`、`getPlayOptions()`、`health()` 和解析纯函数测试；通用预检及缓存位于共享验证层，不能把 HTTP/授权判断复制到各个适配器。

## 排序与界面

文本相关性仍先于来源数量和流行度。可播放性是硬门槛；来源可靠性只在已通过门槛的同等匹配结果之间作为加分。推荐原生 stream 的优先级高于官方 iframe，但用户点选了某一具体来源时必须尊重选择。

搜索页新增 Openverse、Commons 两个来源筛选按钮，并保持 Archive、B站和本地的独立开关。来源行保持既有“歌曲名 · 歌手 / 发布者 · 来源 · 时长”结构；开放来源增加紧凑的授权标识和“查看授权”外链。无可播放结果时，应明确说明是“未找到可播放版本”，而非暗示歌曲不存在。

来源管理页显示：健康状态、过去窗口的搜索成功率、预检成功率、最近失败原因与可重试状态。它不展示用户密钥，也不要求用户登陆第三方服务。

## 错误处理与性能

- 每个网络来源独立超时；一个来源限流、429 或网络错误只加入 `errors[]` 和来源管理状态，不清空其他结果。
- 预检缓存按 URL/来源保存，成功和失败使用不同的短 TTL；失败缓存防止每次输入都重复请求死链。
- 预检只读取最小 Range，不跟随到大文件下载；重定向次数、响应体字节数和并发数都有上限。
- Openverse 匿名访问若遇到限流，自动降级为该次搜索跳过并保留来源状态提示，不使用或内置私人 token。
- 授权、来源页与发布者信息缺失的开放音频不显示为“可验证结果”。

## 验收标准

1. Archive 搜索结果中，点击播放的条目具备至少一个通过预检的原生音频选项；死链/无音频文件的条目不会出现在结果里。
2. Openverse 与 Commons 能分别搜索、展示并播放开放授权音频；每条结果可查看来源/授权信息。
3. 关闭任一来源筛选后，统一搜索不会请求该来源；部分来源失败不会影响 Bilibili、本地或其他可用来源。
4. 原生 stream 播放失败后能换源，并在短期内不再被自动选为最佳来源。
5. 搜索、播放、队列、主题和现有 Bilibili 官方嵌入行为不回归；不新增抖音爬虫、媒体下载、代理转码或绕过访问限制。
6. 后端适配器/验证层单元测试、前端来源筛选与授权展示测试、TypeScript 检查和生产构建通过。
